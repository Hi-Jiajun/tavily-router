# 调优记录（性能优先）

目标：降低客户端可见的 429 比例。范围：网关与 nginx 配置，不更换上游程序。

## 结论摘要

| 项 | 调优前 | 调优后 | 依据 |
| --- | --- | --- | --- |
| 响应缓存 | 关 | 开，TTL 1 小时（仅 `POST /search`） | 同一 query 第 2 波 6/6 本地命中，耗时 4.40s→1.04s，不再消耗上游额度 |
| 额度自动同步 | 关（选路基于旧数据） | 每 15 分钟，`request_interval_seconds=1` | 选路依据准确；远低于 `/usage` 的 10 次/10 分钟限制 |
| 请求日志保留 | 30 天 | 7 天 | 日志含 query 与响应正文，缩短落盘面 |
| 入口整形 | 无 | 12 req/s + burst 120 排队（`limit_req`） | 100 并发实测：停用 0.06s 全放行（上游被打爆）；启用后 8.29s 内 0 个本地 429 全放行 |

## 为什么是 12 req/s

实测单把 development key 顺序发送约 3 req/s 可长期通过（130 次 / 42s 全部 200，≈187 RPM，
高于文档写的 100 RPM），而突发并发 ≥24 会出现非确定性 429。稳态上限按 key 数线性外推
（每把 key ≈3 req/s），配置里取 12 req/s 作为示例值。`burst=120` 的作用是让 100 量级的
突发**排队**而不是被本地 429 掉。

## 一个错误配置与它的教训

最初用 `rate=8r/s + burst=40`：100 并发时只有 41 个通过、59 个被 nginx 自己 429 掉——
等于把"上游 429"换成了"本地 429"，对降低错误率毫无收益。把 `burst` 提到 120 后，
同样的 100 并发全部排队放行、0 个本地 429。

**教训**：限速区的 `burst` 必须不小于你希望"绝不失败"的突发规模，否则它只是在换一个地方报错。

## 代价（必须知情）

| 指标 | 调优前 | 调优后 |
| --- | --- | --- |
| 429 率（2 波 × 20 并发） | 0% | 0% |
| p50 延迟 | 1.53s | 2.95s |
| p95 延迟 | 2.33s | 4.12s |

也就是说，在 ≤20 并发这个量级，入口整形**只增加延迟、不减少 429**（两态均为 0%）；
它的价值出现在 24 并发以上的重突发：把上游的非确定性 429 变成可控的排队等待。

## 可调旋钮

| 想要 | 怎么改 |
| --- | --- |
| 更低延迟 | 调小 `burst`，或给 `limit_req` 加 `nodelay`（突发直接放行，代价是更容易撞上游限速） |
| 更高吞吐 | 增加上游 key 数，并同步提高 `rate`（按每把 key ≈3 req/s 估算） |
| 更省额度 | 加大缓存 TTL；对实时性要求高的请求加 `no_cache=true` 查询参数绕过缓存 |
