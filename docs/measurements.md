# 限速与计费实测

环境：单把 development key；所有请求经网关出网，出口为同一公网 IP。

## 限速行为

| 实验 | 结果 |
| --- | --- |
| 130 次真实请求**顺序**发送 / 42s | 全部 200（≈187 RPM） |
| 150 次**非法**请求（空 query）并发 12 | 全部 400，且不影响随后的正常请求 → 无效请求不计入限速窗口 |
| 24–130 并发真实请求 | 有时 100% 成功，有时 100% 429 → **非确定性**，与最近一分钟的累计量相关 |
| 429 的计费 | **不计费**（额度读数不变） |
| 触发后的恢复 | 数秒～约 1 分钟；20s 间隔探测 6/6 恢复 200 |

结论：这不是严格的"每分钟 N 次"计数器，而是对突发/并发形态敏感的窗口计数。
顺序、稳定的速率可以长期通过；成批并发容易被拒。

## 限速的作用域：按 key，不按 IP

决定性实验：先冲击 key A 直到 429，**同一秒内**用 key B（另一账号）从两个不同出口 IP 探测：

| 探测路径 | 结果 |
| --- | --- |
| Key B，出口 IP #1 | 200 |
| Key B，出口 IP #2 | 200 |

即：A 被限速完全不影响 B。曾有一轮观察到 A、B 同时 429，但**未能复现**，
故不能完全排除存在短暂共享成分。实践含义：多 key 既能叠加额度，也能叠加可用并发；
多出口 IP 的收益不明显。

## 计费口径

| 项 | 文档 | 实测 |
| --- | --- | --- |
| `extract` | 1 credit / 5 URLs | **1 credit / 次**（130 次调用对应约 131 credits） |
| `429` 响应 | — | 0 credit |

> `/usage` 端点的读数存在**滞后或非累计口径**：曾出现成功承接 25 次请求后仍显示 0，
> 以及读数从 641 回落到 609。因此网关内的 `used_quota` 只能当近似值，
> 真正的额度闸门以 Tavily 返回的 432/433 为准（网关对这两个码会换 key）。

## 复现方式

```bash
# 顺序稳定性（消耗 = 成功请求数 × 1 credit）
scripts/loadtest.py --entry http://<LAN_ADDR>:8080 --waves 1 --concurrency 1

# 突发形态
scripts/loadtest.py --entry http://<LAN_ADDR>:8080 --waves 2 --concurrency 20

# 先看计划不发送
scripts/loadtest.py --entry http://<LAN_ADDR>:8080 --waves 2 --concurrency 20 --dry
```
